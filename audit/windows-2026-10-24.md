# Qualification de l’application Windows — 24 octobre 2026

## Périmètre livré

Interface native Qt Widgets en français, sept onglets, vidéo reçue directement
en mémoire et affichée sans JPEG/MJPEG. Les services de `app.py` ont été extraits
dans `camera_core.py` pour partager les fonctions avec l’interface web existante.
Les commandes longues passent par un worker borné ; l’aperçu ne reçoit aucune
file d’images. La fermeture attend la fin des écritures/commandes en cours.
Une image ancienne est signalée comme interrompue ; le premier échec de lecture
provoque une reconnexion au lieu d’attendre dix échecs consécutifs.

Le lanceur .NET `SmartCamera.exe` et le script de construction sont fournis.
Le lanceur dépend de l’environnement Python/ML installé dans le projet et ne
constitue pas un installateur autonome de CUDA/Python/poids. Il ne publie pas de
serveur web. Le token est masqué et reste dans le fichier local ignoré par Git.

## Vérifications automatisées

Environnement CPU dédié `.venv-test`, Windows / Python 3.13 :

- `python -m pytest -q --basetemp=.audit-tmp/desktop-tests-delivery` : **85 réussis,
  2 ignorés** (tests de processus/signaux Linux) ;
- `python -m ruff check .` : réussi ;
- `python -m pip check` : réussi ;
- compilation du lanceur avec le compilateur .NET Framework du PC : réussie.

Les nouveaux tests couvrent la propriété mémoire/couleurs de l’image Qt,
la présence des pages sans démarrer caméra/modèles, la réactivité de la boucle Qt
pendant une commande bloquante, le rejet des commandes accumulées, la fermeture
pendant une sauvegarde, la validation et l’atomicité de la configuration,
l’acquittement caméra et la reconnexion dès le premier échec de lecture.
Le sélecteur de modèles a également motivé une correction : le nom du répertoire
parent ne doit pas faire classer un modèle YOLO comme modèle SAM.
Deux tests supplémentaires couvrent la restauration des réglages après une
relance interrompue de l’encodeur et l’attente de libération des workers lors de
la fermeture de la fenêtre.

## Vérification réelle

Environnement `.venv-audit` existant, Qt/PySide6 Essentials **6.12.0**, OpenCV
**4.13.0**, PyTorch CUDA, GPU NVIDIA compatible CUDA et moteur **yolo26n.engine**.
Cet environnement réutilise les bibliothèques ML du PC : ce n’est pas une preuve
de réinstallation propre de toutes les dépendances GPU.

La fenêtre native a été ouverte et inspectée sur Windows : vidéo du Pi affichée,
contrôle authentifié via `192.0.2.10`, moteur CUDA/TensorRT chargé, token masqué,
commandes natives accessibles. Les captures de l’intérieur restent privées.

Deux sessions de 60 secondes ont été mesurées avec
`python -m tools.qualify_desktop --seconds 60 --output …` sur la liaison
WireGuard/réseau mobile utilisée dans la session :

| Mesure | Décodage standard | Option faible latence |
| --- | ---: | ---: |
| Images décodées au dernier échantillon | 981 | 1231 |
| Identifiant de dernière image traitée | 981 | 1231 |
| Première image observée par l’échantillonneur | 12,04 s | 9,03 s |
| Intervalle Qt P95, timer demandé à 10 ms | 10,99 ms | 10,97 ms |
| Plus grand intervalle Qt observé | 283,68 ms | 261,04 ms |
| Échantillons avec image âgée de plus de 3 s | 14 | 5 |

Les mesures confirment la réactivité de l’interface, mais **des pauses réseau
subsistent**. Les essais n’ont pas été conduits en ordre alterné répété : ils
ne prouvent pas un gain causal du profil de décodage. L’option reste donc
facultative : `SmartCamera.exe --low-latency`. Elle transmet les options FFmpeg
avant le lancement de Python, pour éviter les limites de lecture des variables
d’environnement du runtime natif Windows.

Un essai direct supplémentaire de 40 s avec les délais 12 s / 10 s a reçu
1179 images sans échec de lecture. Les délais plus tolérants ont été sauvegardés
dans la configuration locale, après sauvegarde privée ; le débit Pi reste
2 Mbit/s et la résolution 640 × 480. Aucune modification réseau/routeur n’a
été appliquée pour cette livraison.

## Limites conservées

La réactivité Qt et les compteurs de réception ne mesurent pas la latence
optique de bout en bout. Le Pi ne fournit qu’un lecteur TCP vidéo à la fois.
Les options SAM3, VLM, reconnaissance et SMTP sont raccordées aux services
existants ; les tests de cette livraison n’ont pas qualifié de nouveau tous les
modèles ni envoyé d’email. Aucun taux de reconnaissance n’est revendiqué.
Les alertes démarrent désactivées. Les constats de sécurité des dépendances
de l’audit précédent restent applicables.

Les données brutes et sauvegardes restent dans
`.audit-tmp/desktop-qualification/`, ignoré par Git. Guide utilisateur :
[docs/windows.md](../docs/windows.md).

La dernière exécution de 30 secondes avec la fermeture révisée s’est terminée
avec le code 0, après libération du worker caméra ; la boucle Qt est restée à
11,00 ms au P95 (maximum 249,55 ms). Un délai de lecture dépassé et une erreur de
décodage ont encore été observés pendant cette exécution. La relance contrôlée
de l’encodeur a auparavant rétabli un port vidéo devenu inaccessible, avec
restauration vérifiée des réglages 640 × 480 / 30 / 2 Mbit/s. Cette commande est
maintenant disponible explicitement dans l’onglet Caméra ; elle n’est jamais
déclenchée automatiquement lors d’un simple problème réseau.
