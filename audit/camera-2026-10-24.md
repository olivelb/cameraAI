# Qualification réelle Pi Zero — 24 octobre 2026

## Résultat

La chaîne Pi → H.264/TCP → client Windows → YOLO/TensorRT CUDA → MJPEG Gradio
a fonctionné sur les images de la caméra. Le serveur du Pi a été mis à jour
après sauvegarde et autorisation explicite d'interrompre le service `camera`.
Le Pi n'a pas été redémarré.

État final vérifié : service `camera` actif, un processus `rpicam-vid`,
640×480 à 30 i/s demandées, 2 Mbit/s, contrôle authentifié, `throttled=0x0`.
Le frontend de qualification sur localhost a été fermé après les essais ;
le service Pi reste prêt à recevoir le client habituel.

Ces essais courts démontrent le fonctionnement et les récupérations décrites.
Ils ne qualifient ni la précision de reconnaissance ni une endurance continue.
Le risque Pillow signalé par l'audit initial reste ouvert.

## Problèmes révélés et corrections

1. **Le client ne joignait pas le Pi.** Le `pi.host` local pointait vers un nom
   non résolu. Une connexion de maintenance a permis de vérifier une autre voie
   d’accès. La configuration locale a été corrigée après sauvegarde.
   Aucun repli automatique vers une machine différente n'a été ajouté au code.
2. **L'ancien serveur était resté installé.** Il n'authentifiait pas les commandes,
   n'envoyait pas d'acquittement et masquait stderr. Déploiement du serveur audité,
   unité systemd corrigée et même token que le client, transféré sans affichage.
   La configuration Pi est dédiée aux sections `server` et `camera`. L'ancienne
   configuration complète est conservée dans la sauvegarde.
3. **L'arrêt au SIGTERM pouvait attendre une activité réseau.** Un premier arrêt
   du serveur audité a dépassé 20 secondes et le processus est resté actif plus
   d'une minute. `signal.signal` appelait directement `asyncio.Event.set`, sans
   réveiller le sélecteur endormi. Le signal utilise maintenant
   `loop.call_soon_threadsafe`, arrête le watchdog immédiatement et borne la
   fermeture WebSocket. `TimeoutStopSec=15` fournit aussi une limite systemd.
4. **Le mode photo 2592×1944 était offert comme mode vidéo.** Son essai à 10 i/s
   a échoué avec `failed to start output streaming`. Le mode reste descriptible
   comme résolution du capteur, mais il est exclu de `stream_resolution_set`,
   du menu client et du serveur H.264, y compris avec une ancienne configuration.
5. **La demande de priorité échouait.** `nice -n -10` produisait `Permission denied`
   sous le compte normal. Suppression de cette demande ; aucun privilège
   supplémentaire n'a été accordé et aucun gain CPU non mesuré n'est revendiqué.
6. **Le contrôle pouvait attendre une terminaison d'enfant.** Séparation du verrou
   de réglages et du verrou de gestion des processus, pour que le thread asyncio
   ne se bloque pas sur un `wait` du watchdog.
7. **Un mauvais token ne recevait pas de réponse.** Réponse `unauthorized` explicite,
   comparaison du token adaptée aux entrées UTF-8 et affichage du motif côté client.
   Les trames binaires UTF-8 invalides sont ignorées proprement.
8. **Le délai d'ouverture était trop court pour le flux brut.** Une analyse H.264
   normale a demandé environ 6–7 secondes. Ouverture maintenant configurable à
   7000 ms, attente de lecture à 3000 ms, politique commune dans `capture.py`.
9. **La tâche TensorRT était devinée.** Le chargement affichait un avertissement
   et pouvait supposer `detect` pour un moteur de segmentation. Le client fournit
   explicitement `detect` ou `segment` au chargement `.engine`.

La scène de qualification ne contenait aucun sujet des classes personne/chat/chien ;
les sorties vides sont donc une preuve d'exécution, pas de qualité de détection.
Les tests automatisés Windows passent avec les deux régressions Linux ignorées ;
leurs frontières natives (`flock` et arrêt SIGTERM) ont été exercées directement
sur le Pi. Une régression Linux spécifique au sélecteur inactif a été ajoutée à la CI.

Les valeurs `received_fps` du JSON comprennent le vidage du tampon de démarrage
et peuvent dépasser la cadence demandée. Les FPS affichés par l'IA ne mesurent
que l'inférence. Aucune de ces valeurs ne représente une mesure de cadence
physique ou de latence caméra→écran.

## Réglages de décodage étudiés

Un A/B dans **des processus séparés**, avec les mêmes réglages caméra, a mesuré :

| Variante | Première image, répétition 1 | Répétition 2 |
| --- | --- | --- |
| FFmpeg par défaut | 6,10 s | 6,11 s |
| `analyzeduration;100000\|probesize;32768\|fpsprobesize;0` | 4,96 s | 4,99 s |

Le gain observé est d'environ 1,1 seconde sur cette scène et ce profil. Modifier
la variable depuis Python après le démarrage du runtime natif Windows ne
reproduisait pas ce résultat ; les essais négatifs sont conservés. Ce réglage
n'est **pas** imposé par défaut. Pour le reproduire, définir la variable dans
le shell **avant** le lancement :

```powershell
$env:OPENCV_FFMPEG_CAPTURE_OPTIONS='analyzeduration;100000|probesize;32768|fpsprobesize;0'
python app.py
```

Un seul thread de décodage n'a pas apporté de gain reproductible ; ce changement
n'a pas été retenu. Pas de modification du débit, des seuils IA ou du nombre
d'images clés à partir de ces seuls essais.

  décrivent l’état historique qualifié, avant anonymisation des exemples. Les
  modèles de configuration distribués peuvent donc différer. Elles sont consignées dans
  [camera-2026-10-24.json](camera-2026-10-24.json), avec les résultats structurés.

  `/path/to/private-backups/2026-10-24-before-qualification/`.
  Elle contient les anciens scripts, la configuration et l'unité systemd.
- Exemple de dossier de préparation et mesures natives, à adapter :
  `/path/to/private-staging/`.
- Journaux, essais négatifs, versions, sauvegarde locale et captures de la pièce :
  `.audit-tmp/pi-2026-10-24/`, ignoré par Git. Ces données sont conservées localement.
  Aucune photo de la pièce, aucun token ni réglage privé n'est inclus dans les fichiers suivis.
- Commande de requalification : `python -m tools.qualify_pi --output ...`.
  L'option `--profiles` est explicitement nécessaire pour changer les réglages.
